AIの実行を、共通の制御下へ

Managed Harnessは、AIが何を答えたかではなく、Workspaceへ何を実行したかを管理するための境界です。Providerが変わっても、ファイル操作、Command、承認、監査を共通の契約で扱います。

Providerごとに独自のfile toolやshell toolを直接実行すると、Access設定、監査、失敗時の扱いがばらばらになります。Sprint Coderは副作用をMain側の共通経路へ集約し、UIから同じ考え方で確認できるようにします。

なぜProvider共通のHarnessが必要か

Codex CLI、Claude Code、公式API、互換APIでは、tool callの形式やstream eventが異なります。しかしユーザーにとって重要なのは、どのProviderを使ったかより、どのファイルを読み、何を変更し、どのCommandを実行したかです。

Managed HarnessはProvider固有eventを正規化した後、Workspace toolとCommand runnerへ接続します。これにより、modelを変えてもTaskのAccess方針と監査の見方を変えずに済みます。

生成から実行までの経路

  1. Providerがtool callを生成する

    選択されたmodelが、必要なファイル操作やCommandを要求します。

  2. Runtimeが共通eventへ正規化する

    Provider固有の形式を、Sprint Coderが扱うcanonical eventへ変換します。

  3. Tool Brokerがpolicyを評価する

    TaskのAccess、Workspace範囲、tool capability、承認条件を確認します。

  4. 管理された実行器が操作する

    ファイルtoolまたはCommand sandboxが、許可された範囲で副作用を実行します。

  5. 結果と証拠をTaskへ返す

    成功・失敗、差分、出力、承認履歴をUIから確認できる形へ戻します。

ファイル操作の境界

ファイルtoolは選択したWorkspaceを基準に扱います。読み取り、作成、更新はpath guardとscopeを通し、差分として確認できる状態へつなげます。単純な文字列prefixだけで安全性を判断せず、正規化されたpathとWorkspace境界を使います。

  • Workspace外への意図しないpath逸脱を防ぐ
  • 変更内容をTaskの差分として確認する
  • 承認要求を対象ファイルと操作へ結び付ける
  • 途中失敗時も結果を曖昧な「完了」にしない

Command sandboxと承認

CommandはOS環境のsandbox probeとTaskのAccessを確認してから公開します。sandboxを確認できない環境では、危険なcommand toolを利用可能にしたまま進めません。

承認が必要な操作では、理由、対象、実行内容をUIへ表示し、ユーザーの判断を待ちます。承認後の実行結果も同じTurnへ戻し、「許可した内容」と「実際に起きたこと」を追えるようにします。

HarnessはAIの正しさを保証するものではない

実行境界と証拠を揃える仕組みです。生成された変更の設計品質や要件適合性は、テスト、差分review、必要に応じた独立reviewで確認してください。
