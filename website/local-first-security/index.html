LOCAL-FIRST & SECURITY

Local-firstと安全性

Local-firstは『常にオフライン』という意味ではありません。Sprint Coderは履歴と実行状態を端末内で管理し、ユーザーが選んだProviderとAccess設定に応じて外部送信とWorkspace操作の境界を変えます。

安全性を考えるときは、「どこに保存されるか」「どこへ送られるか」「何を実行できるか」を分ける必要があります。Sprint Coderはこの三つをTask、Provider、Accessの設定として明示します。

Local-firstが意味すること

Task、Message、Turn、Teamの状態やアプリ設定は、基本的にユーザーの端末内へ保存されます。UIを閉じたりアプリを再起動したりしても、同じTaskを続きから再開できるようにするためです。

一方で、クラウドProviderを使う場合、AI生成に必要なpromptやcontextは選択した接続先へ送信されます。local-firstはクラウド利用を隠す表現ではなく、保存の正本と送信先をユーザーが選べる設計です。

保存される情報と送信される情報

情報 端末内 外部送信
Task履歴・実行状態 ローカルへ保存 同期サービスは標準前提ではない
prompt・生成context Task履歴として保持 クラウドProvider選択時に送信
Workspaceファイル ユーザーのWorkspaceに存在 modelへ必要なcontextとして渡る場合がある
診断ログ ~/.sprintcoder/logs/等へ保存 自動的な第三者共有を前提にしない
機密情報を含むTask

Providerのデータ利用条件と組織のポリシーを確認し、必要ならローカルLLMを選択してください。第三者へ診断ログを渡す前にも内容を確認してください。

API keyとRendererの境界

API keyはRendererへ長期間保持せず、Main process側でElectronのsafeStorageを使って端末内へ保存します。Rendererはsandboxとcontext isolationを有効にし、Node.js APIを直接公開しません。

接続先のBase URLも無制限ではありません。公式Providerや設定した互換endpointを使うときは、接続検証とegress policyを通します。実装上の確認項目はSecurity Checklistで公開しています。

Workspace操作をTask単位で制御する

Workspaceへ影響する操作は、TaskのAccess設定とManaged Harnessを通じて扱います。入口となるAccessは、確認を挟む運用、自動実行を許す運用、より広いアクセスを与える運用を選べます。

どのAccess設定でも、OSや環境側のsandbox確認に失敗した場合は、危険なcommand toolをそのまま公開しない設計です。early betaであることも踏まえ、重要な操作では差分と実行内容を確認してください。
