詳しい話

Local-firstが意味すること

Local-firstは「常にオフライン」という意味ではありません。Sprint Coderは履歴と実行状態を端末内で管理し、ユーザーが選んだProviderとAccess設定に応じて、外部送信とWorkspace操作の境界を変えます。安全性を考えるときは「どこに保存されるか」「どこへ送られるか」「何を実行できるか」を分ける必要があり、Sprint Coderはこの三つをTask、Provider、Accessの設定として明示します。

Task、Message、Turn、Teamの状態やアプリ設定は、基本的にユーザーの端末内へ保存されます。UIを閉じたりアプリを再起動したりしても、同じTaskを続きから再開できるようにするためです。

一方で、クラウドProviderを使う場合、AI生成に必要なpromptやcontextは選択した接続先へ送信されます。local-firstはクラウド利用を隠す表現ではなく、保存の正本と送信先をユーザーが選べる設計です。ローカルLLM（Ollama、LM Studio、LocalAI）を選べば、生成は端末内で完結します。

保存される情報と送信される情報

データ保存と送信の境界
情報端末内外部送信
Task履歴・実行状態ローカルへ保存同期サービスは標準前提ではない
prompt・生成contextTask履歴として保持クラウドProvider選択時に送信
WorkspaceファイルユーザーのWorkspaceに存在modelへ必要なcontextとして渡る場合がある
診断ログ~/.sprintcoder/logs/等へ保存自動的な第三者共有を前提にしない

機密情報を含むTaskでは、Providerのデータ利用条件と組織のポリシーを確認し、必要ならローカルLLMを選択してください。第三者へ診断ログを渡す前にも内容を確認してください。

API keyとRendererの境界

API keyはRendererへ長期間保持せず、Main process側でElectronのsafeStorageを使って端末内へ保存します。Rendererはsandboxとcontext isolationを有効にし、Node.js APIを直接公開しません。

接続先のBase URLも無制限ではありません。公式Providerや設定した互換endpointを使うときは、接続検証とegress policyを通します。実装上の確認項目はSecurity Checklist（GitHub）で公開しています。

Workspace操作をTask単位で制御する

Workspaceへ影響する操作は、TaskのAccess設定とManaged Harnessを通じて扱います。入口となるAccessは、確認を挟む運用、自動実行を許す運用、より広いアクセスを与える運用を選べます。

Access設定と監査
設定考え方向いている使い方
確認する操作ごとに判断ファイル変更やCommandの前に内容を確認したいTask
自動許可範囲で進行定義された範囲内の操作を止めずに進めたいTask
フルアクセス広い権限を明示信頼できるWorkspaceで、必要性を理解して選ぶ設定
監査実行を画面へ残す差分、Command、承認履歴をTaskの仕事として確認

どのAccess設定でも、OSや環境側のsandbox確認に失敗した場合は、危険なcommand toolをそのまま公開しない設計です。重要な操作では差分と実行内容を確認してください。

関連する仕組みとして、Managed Harnessはファイル、Command、承認、監査を共通経路で扱う設計です。使えるAIはAIの選び方で、Codex、Claude Code、Gemini、API、ローカルLLMの選び方を説明しています。
