# Windows ブラウザのページ受入（#988 N11 F4 段 A）

この文書は、人が Windows 実機で確かめる手順である。
受入結果ではない。全項目の初期状態は **未確認** とする。
共通の準備と証拠の扱いは [共通手順](README.md) に従う。
背景入力の準備は [P7b の手順](windows-background-p7b-tools.md) を参照する。

## 今の状態

基準は F3b（PR #1150、head `e6ce57f5`）に F4 段 A の未 commit 差分を加えたもの。
**正規配置・署名を確認した Chrome・Edge だけが supervised（操作ごとの承認付き）の対象**である。
ruleset／classifier／lexicon は **5／4／3**。full_access_app へは開放しない。
Firefox とその他ブラウザの閲覧限定、Electron・WebView2・CEF の既存の対象範囲は維持する。
ブラウザを操作できても copy と artifact の貼付けは許可しない。

origin は通信方式・ホスト・ポートで決まるページの出所を指す。
sensitive（機密）・unknown（判定不能）、localhost／IP アドレス、機密欄は入力不可。
通常 HTTP(S) でも、ページと対象要素の完全な証拠、規則による判定、単発承認がすべて必要になる。
observe_only は観測だけのモードであり、承認カードで制限を迂回できない。
Main は native が既知フォルダーと正規化した配置を検証した上限を使い、共有規則・承認能力でさらに絞る。
ProgramW6432 等の環境変数の欠落だけを理由に native と異なる上限にはしない。
Main でも実行ファイルのパス末尾が native の imageRelativePath と一致するか確認し、不一致は観測のみに絞る。
再承認の判断は保存版ではなく、保存した許可の上限と現在の上限の比較で行う。
現行 ruleset 5 で観測のみとして保存した許可も、現在 supervised が可能なら再承認できる。
上限が変わらない既存許可は再承認不要。上限を広げるカードを拒否しても、同じ Task で従来の観測許可は使える。

入口で拒否された結果と、ページ変更の再確認で止まった結果は分ける。
必要な段階まで到達できなければ、その再確認の項目は BLOCKED とする。
制限を解除したり、内部状態を書き換えたりして先へ進めない。

## 実機での準備

1. 対象 build の commit、未 commit 差分、配布形式、Windows の版を記録する。
2. ブラウザ名と版を記録する。Chrome・Edge は必ず別々に実施し、Firefox 等は閲覧限定の負のケースとして記録する。
3. 普段の利用環境から分離したプロファイルを用意する。
4. 秘密情報のない通常 HTTP(S) の試験用ページを用意する。以下では名前を P1・P2・P3 とする。localhost は正のケースに使わず、拒否専用の fixture にする。
5. P1 と P2 は同じ origin の別タブにする。P3 は異なる origin にする。
6. 確認文を変更できるページと、機密欄を持つ合成ページを用意する。
7. ページの切替は人が画面から行う。実際の購入・送金・認証は行わない。
8. 対象の窓を選び、観測結果と操作モードを確認する。
9. 各項目の開始前に観測し直す。前の項目の承認を使い回さない。

試験用ページは fixture（再現用の合成データ）で用意する。
機密状態への変化は、分類器が sensitive と判定する fixture を使う。
単にページへ「機密」と表示しただけでは、その前提を満たさない。
読み取り専用の診断で前提を確認できなければ BLOCKED とする。
実 Provider を使う確認は、別途明示された許可がある場合だけ行う。

UIA は、Windows がアプリの要素を読み取ったり操作したりする仕組みを指す。
ページの同一性は origin だけでなく、Document（ページ要素）の識別情報と場所で照合される。
人の目では分からない照合や入力時点は、既存の受動的な診断を併用する。
診断が使えない場合も、入力が見えなかっただけで再確認を PASS にしない。
Chrome での結果を、Edge や Firefox の対応済みという根拠にしない。

## 結果の記録

| 状態    | 意味                                                             |
| ------- | ---------------------------------------------------------------- |
| PASS    | 必要な前提・操作時点・期待を証拠で確認した。                     |
| FAIL    | 前提が成立した状態で、実際の動作が期待に反した。                 |
| BLOCKED | 制限、fixture 不足、計測不能などで必要な段階を確認できなかった。 |
| 未確認  | まだ試していない。本書の全実機ケースの初期状態。                 |

次の形で、項目・ブラウザ・操作時点ごとに記録する。

```text
項目 ID／状態: B-xx / 未確認
日時／Windows の版:
build の commit／未 commit 差分／配布形式:
ブラウザ名／版（Electron はアプリ名／版）:
操作モード／fixture ID:
手順／変化・停止の時点:
期待／実結果／拒否理由:
証拠の保存先／BLOCKED の理由／残件:
後片付け:
```

**URL・ホスト名・ページや窓のタイトルは記録しない。**
ページは P1・P2・P3、分類は sensitive・unknown などの状態だけで記録する。
画像にもアドレス欄、タブ名、窓タイトルが入らないようにする。
診断の生データを添付せず、許された最小限の状態と件数だけを残す。
build 成功や自動試験の成功を、実機の PASS に置き換えない。
