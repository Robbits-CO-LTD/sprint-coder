# 反証パターン

この資料は、2026年5月11日から8月14日までに保存されていたClaude/Codexログを基にした。初回調査では2,150件のClaude JSONLと4,636件のCodex JSONLを列挙し、内部サブエージェント、ツール結果、自動通知、委譲文、注入指示を除外した5,291件の人間発言から反復傾向を抽出した。ログは作業中も増えるため、件数はこの抽出時点の記録として扱う。

履歴はレビュー観点であり、現在の依頼より優先しない。個別プロジェクトの状態、モデル、Issue番号、パスは実行時に現物を確認する。

## 中心となる二つの補正

### 広げすぎを止める

深く考えるほど、受入条件にない安全策、抽象化、テスト、レビューを追加し、仕事が終わらなくなる傾向を警戒する。

反証の問い:

- これは今回の受入条件を直接満たすか。
- 具体的な故障仮説があるか。
- この追加作業がなくても、対象リスクを直接確認できないか。
- 完了条件が後から増えていないか。

匿名化した典型例: 局所修正が数千行の基盤拡張へ膨らんだため、実環境の主要経路と固定した少数の検証へ完了条件を戻した。

### 忘れ物を閉じる

実装や説明が速くても、公開、ラベル、マージ、実機確認、readback、cleanupなど、依頼された最後の一歩を忘れる傾向を警戒する。

反証の問い:

- 「完了」の各語が義務台帳のどの証拠に対応するか。
- 作成しただけで、反映・公開・再読を確認していないものはないか。
- 最初の依頼と途中の追加依頼が最終成果物に残っているか。
- 別checkout、古い版、予定状態を現在状態と取り違えていないか。

匿名化した典型例: 判定報告は正しかったが、利用開始に必要な実装計画の公開と状態ラベルがなく、実務上は未完了だった。

## 反復する指摘の型

| 型 | 先に疑う主張 | 有効な反証 |
| --- | --- | --- |
| 途中停止 | 「調査・計画・PR作成までで依頼を満たした」 | 依頼文の動詞と終点を列挙し、未実施工程を照合する |
| 偽の完了 | 「テスト成功だから完了した」 | 利用者が見る状態、live state、公開先、異常系を同じ版で確認する |
| stale evidence | 「以前のログや別作業場所が現在を証明する」 | 対象、版、時点、環境の4点を一致させる |
| 症状対処 | 「見える症状が消えたから原因も解決した」 | writer、競合、切替、失敗伝播、再発条件を別経路で確認する |
| 過剰検証 | 「多く試すほど安全」 | 変更箇所と故障仮説に直接効く最小検証へ戻す |
| スコープ越境 | 「良さそうな改善だから今回も実施する」 | 必須、防御、別Issue候補へ分離する |
| 人間境界の越境 | 「作業を進めるため入力・保存・承認を代行してよい」 | 現在の明示的な禁止と承認者を再読する |
| UIの断絶 | 「機能するから使いやすい」 | 移動の連続性、見切れ、長文表示、状態遷移を目視する |
| 自然さ不足 | 「機械QCが通るから品質も十分」 | 人間の動き、間、視線、画面遷移、利用状況で確認する |
| 決定の消失 | 「現在コードが正本だから過去決定は不要」 | 承認済み要件と現行成果物を項目単位で比較する |

## 誤検知を防ぐ境界

- 計画に書かれた将来の追加物が現在存在しないことは欠陥ではない。
- 明示的な対象外やHuman Gateを、漏れとして強制実装しない。
- 既存問題は、今回の変更で悪化するか受入条件を妨げる場合だけ指摘する。
- 好みや一般論だけでは指摘しない。利用者影響または具体的な故障経路を示す。
- 反証できなかった弱い推定を、確認済みの事実として書かない。
- 過去の好みが現在の明示指示と衝突する場合、現在の指示を採用する。

## UI・成果物で優先する感覚

- 移動前と移動後を短いモーションでつなぎ、急に消えた感覚を避ける。
- 長い名前や重要情報は、省略や非表示より全文表示と横スクロールを優先する。
- 数値上の成功だけでなく、自然さ、生活感、間、使い勝手を確認する。
- 技術用語中心の説明ではなく、利用者が「何が終わり、何が残るか」を一読できる形にする。

## 反証の停止条件

次をすべて満たしたら追加探索を止める。

1. 必須義務に現行の直接証拠が対応している。
2. BLOCKER/HIGH候補へ反証試行を行い、未解決がない。
3. 追加検証の故障仮説が残っていない。
4. 明示された終点と後始末へ到達している。
5. 新しい指摘が既存指摘の言い換えになっている。
