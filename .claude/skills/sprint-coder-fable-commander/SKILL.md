# Fable 5.2 司令塔 + Opus 5.5 子分

## 目的

狙いは速さである。Fableが一人で順番に進めるより、独立した塊を子分に同時に走らせ、Fableは判断が要る部分だけを持つ方が早く終わる。グローバルの `commander` / `fable-commander` はトークン節約が目的でSonnetを主力にするが、このSkillは完了までの時間を縮めるためにOpus 5.5を子分にする。

## 適用条件

次のすべてを満たすときに適用する。

- 自分のモデルがFable 5.2である。システムプロンプトのモデル表記（`claude-fable-5-2`）で確認し、表記が無い・別モデルの場合は推測で適用せず、通常どおり作業する。
- 自分がメインセッションである。サブエージェントとして起動されている側は子分なので、再委譲せず自分で実行する。
- 作業が複数ステップで、独立に進められる塊が2つ以上あるか、読む範囲が広い。

委譲には依頼文を書く時間と結果を確かめる時間がかかる。数回のツール呼び出しで終わる作業、対象が既に分かっている調べもの、一問一答は、Fableがそのまま片付ける方が速い。

## 役割分担

| 担当 | 持つもの |
|---|---|
| Fable 5.2（司令塔） | 依頼の理解、分解、依頼文の作成、進行管理、成果の監査、統合、ユーザーとの対話、push・PR・merge・Issue投稿などの外向き操作 |
| Opus 5.5（子分） | 調査、テスト実行と検証、独立レビュー。下の条件を満たす塊の実装 |
| Codex CLI | 実装、修正、試験の追加（既定） |

Opus 5.5の子分は `Agent` ツールに `model: "opus"` を付けて起動する。検証・実装は `subagent_type: "general-purpose"`、広い読み取り検索は `subagent_type: "Explore"` を使う。Codexへの依頼は `codex` Skill、または `codex:codex-rescue` を使う。

## 実装の担当

実装の既定はCodexである。Claude側で実装すると利用上限に早く届くため、[AGENTS.md](../../../AGENTS.md) の「役割分担（コードは Codex、Claude は指揮）」がそう定めている。

Opus 5.5に実装させてよいのは、次のどちらかに当たる塊だけである。

- 同じ塊をCodexに2回任せても直らなかった。
- ユーザーが急ぎだと伝えた作業で、独立した塊を同時に進めると完了が早まる。

Opus 5.5に実装させたときは、どの塊をどちらの理由で回したかをユーザーへの報告に書く。利用枠の減り方をユーザーが追えるようにするためである。

調査、検証、レビューはこの制限の対象外で、いつでもOpus 5.5に出してよい。

## 進め方

1. **分解する。** 触るファイルが重ならない塊に分ける。別の塊の結果が要るものは同時に出さず、順番に出す。分け方が決まらないほど不明点が多いなら、先に調査だけを子分に出す。
2. **同時に起動する。** 独立した塊は1つのメッセージにまとめて起動する。書き込みをする担当が2体以上なら、Opus 5.5には `isolation: "worktree"` を付け、Codexにも別々のworktreeを渡す。同じcheckoutで2体が書くと互いの変更を壊す。
3. **待つ間は重複しない。** 子分に出した作業をFableが並行してやり直さない。委譲していない部分や統合の準備を進める。届いていない結果を予測して報告しない。
4. **監査する。** 子分やCodexの報告は主張であり、証拠ではない。diffはFableが自分で読み、テストは実行結果の出力で確かめる。影響の大きい変更は、実装した担当とは別のOpus 5.5に、結論を渡さずdiffだけを渡してレビューさせる。
5. **統合する。** worktreeのブランチを作業ブランチへ取り込み、衝突を解消し、関連するテストをまとめて流す。
6. **報告する。** 何が終わり、何を確かめ、何が未確認かをユーザーに伝える。

同時に動かすOpus 5.5は6体までを目安にする。一度に多く走らせると利用枠を短時間で使うので、それ以上が要るときは先にユーザーへ一言伝える。`Workflow` ツールはユーザーが明示的に求めたときだけ使う。

## 依頼文に入れるもの

子分もCodexもこの会話を見ていない。依頼文だけで動けるように、次を自分の言葉で書く。

- ゴールと、何をもって完了とするか
- 対象のファイル・範囲と、触ってはいけない範囲
- 既に分かっている事実と、既に除外した仮説
- 検証方法（流すテスト、確認するログ）
- 返してほしい形（変更したファイル、実行したコマンドとその結果、未確認の点）
- 最初に [AGENTS.md](../../../AGENTS.md) を読むこと
- push、PR作成、Issue投稿、mergeはしないこと（外向き操作は司令塔が持つ）

Sprint Coder固有の落とし穴も、該当するものを伝える。

- Node.js 22を使う。PATH上のnodeが別バージョンのことがある。
- 新しいworktreeではnative依存が未準備である。`npm run prepare:desktop --workspace @sprint-coder/desktop` を先に流さないと、アプリ不具合に見える失敗が出る。
- Vitestはファイル単位で実行する。SQLite・Electron bridgeを使うテストは名前での絞り込みが効かないことがある。
- UI・E2EのためにPlaywrightのコードを足さない。
- 既に動いているdev serverやアプリは他のcheckoutのものかもしれないので止めない。
- 実Providerの課金を伴う検証は、ユーザーが今回の依頼で明示した場合だけ行う。

## 子分に出さないもの

- **Computer Useによる画面検証。** 画面と操作権は1つしかないので、Fableが直列に行う。fixture準備やログ照合は子分に出してよい。
- **ユーザーへの確認が要る判断。** 仕様の選択や不可逆な操作の可否は、Fableがユーザーに聞く。
- **push、PR、レビューBOT対応の最終判断、merge。** [CLAUDE.md](../../../CLAUDE.md) の開発ワークフローどおりFableが行う。

## 詰まったとき

担当が失敗したら、まず報告を読んで原因を分ける。依頼文の情報不足なら、不足を補って同じ担当に続けさせる（Opus 5.5なら `SendMessage`。文脈が残っているので速い）。Codexが同じ塊で2回直せなかったら、Opus 5.5に実装を回す。Opus 5.5でも直らなければFableが引き取る。不具合修正は原因が確定するまで実装に進めない（`root-cause-guardrail`）。

## 他のSkillとの関係

- ユーザーが指定したSkillが担当モデルを決めている場合は、そのSkillに従う（例: `issue-graph-flow-codex` の実装担当はCodex）。
- グローバルの `commander` / `fable-*` 系をこのリポジトリでFable 5.2が使うときは、Sonnet担当の調査・検証をOpus 5.5に読み替え、実装は上の「実装の担当」に従う。それらにあるOpus 4.8向けの役割制限は、Opus 5.5には当てはめない。
- [CLAUDE.md](../../../CLAUDE.md) と [AGENTS.md](../../../AGENTS.md) のPR、レビューBOT、検証の規則は、このSkillの下でもそのまま守る。
