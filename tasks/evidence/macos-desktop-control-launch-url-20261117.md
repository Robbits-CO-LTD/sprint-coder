# macOS の `launch --url` と、前面を戻す処理の実機の確認（2026-11-16〜17）

[PR #1337](https://github.com/Robbits-CO-LTD/sprint-coder/pull/1337) を merge するまでの実機の記録と、その後にオーナーの了承で行った、害のないアプリでの確認の記録。

## 環境と、この記録の位置づけ

- macOS 27.0.1（Apple シリコン、Retina の内蔵 display）。開発版（dev build）。隔離した profile。
- ブラウザーは Google Chrome（前から動いている状態）。Chrome に example.com の窓を開くことは、オーナーの了承を得た範囲で行った（合わせて 9 回）。
- オーナーが同じ Mac を使っている最中に流した。前面のアプリや入力の有無は、その時々のオーナーの操作で決まっている。
- 「CLI を直接実行」は、この PR の build の実行ファイルを、開発版の Electron の子として 1 コマンドずつ実行したもの。「製品の経路」は、開発版の Sprint Coder の中の実際の AI に頼み、Main が実行したもの（画面の操作は Computer Use）。
- 実際の AI は Codex CLI の Runtime で、設定のモデルは「Auto」。**実際に使われたモデルの ID は記録に残っていない**（Turn の記録の解決後のモデルの欄が空）。そのため、実 AI の試験の決まり（モデルの ID を特定した lane）で言う合格ではなく、補助の確認として扱う。Claude CLI の Runtime は「ログインが必要」と出るので流していない（未実施）。
- 記録の取り方: アプリの切り替え（前面になった・前面でなくなった・起動・終了）の時刻つきの log、画面上の窓の順番（前から後ろ）、前面のアプリの focus の窓の番号、利用者の入力からの経過時間、Main が記録したコマンドごとの結果と所要時間。

## 1. 前面を戻す処理を足す前（`9acf3d66` までの build）

| #   | 場合                                           | 起きたこと                                                                                                                                                                                                                                                  |
| --- | ---------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 1   | 製品の経路。Chrome が前面（`01e71242`）        | 承認カード（題・対象・URL の全文・注記・「今回のみ許可」「拒否」だけ）は設計どおり。コマンドは終了コード 0、579 ms。結果は `handed_off: true` で、動いている Chrome を指した。**新しい窓が、使っていた Chrome の窓の前に出た**（約 4 秒後に利用者が戻した） |
| 2   | CLI を直接実行。別のアプリが前面（`9acf3d66`） | 起動用の process は 13 ms で終わり、その 44 ms 後に Chrome が前面を取り、そのまま残った                                                                                                                                                                     |
| 3   | CLI を直接実行。Chrome が前面（`9acf3d66`）    | アプリの切り替えは無く、約 0.3 秒後に新しい窓が、使っていた窓の前に出て focus を取った                                                                                                                                                                      |

2 と 3 では、その後に既存の `focus-window` で元の窓を名指すと、0.45 秒で元に戻ることも確かめた。2 の計測中に、利用者が起動の 0.05 秒後に別のアプリへ切り替えていて、「起動の前の前面」へ戻すと利用者の選択を取り消すことが分かった（戻す先を「取られる直前の前面」にした理由）。

- 5 では、戻した 1.2 秒後にもう一度 Chrome が前面になった記録があった。入力の有無を一緒に記録して測り直した 6 では起きなかったので、利用者自身の切り替えと見ている。
- 8 の失敗は、戻す操作が error を返したのか、戻した直後に Chrome がもう一度新しい窓を前に出したのかを、記録から区別できなかった。失敗の中身を debug の log に出すようにした（`ccbbc2d6`）。続きは [Issue #1341](https://github.com/Robbits-CO-LTD/sprint-coder/issues/1341)。
- 7 は `c28fb8ba` の build。merge した head（`ccbbc2d6`）との違いは、debug の log を出す行だけ。
- 4・8・9 と 5 の計測は、利用者が Chrome で作業している最中に新しい窓を前に出すことになり、利用者の入力を一時的に奪った。

確かめていないもの: ブラウザーが動いていない時の起動。Chrome 以外のブラウザー。承認カードを利用者自身が押した直後の起動（7 は、カードの出ないフルアクセスの設定で、Sprint Coder を前面にして流した）。起動と同じ瞬間に利用者が前面を動かした場合の実際の動き（単体の試験で決まりを固定してある）。
