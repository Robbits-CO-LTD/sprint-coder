# macOS のデスクトップ操作の残りの確認（2026-11-17 午後）

[Issue #1320](https://github.com/Robbits-CO-LTD/sprint-coder/issues/1320) の後に残っていた不具合（#1336・#1340・#1344）を直した時の実機の記録。クリップボードの書き込み（#1338）は `macos-desktop-control-clipboard-20261117.md` にある。

## 環境と、この記録の位置づけ

- macOS 27.0.1（Apple シリコン）。開発版（dev build）。オーナーが同じ Mac を使っている最中に流した。
- 「CLI を直接実行」は、その PR の build の実行ファイルを、開発版の Electron の子として 1 コマンドずつ実行したもの。「製品の経路」は、開発版の Sprint Coder（隔離した profile）の中の実際の AI が、承認カードを経て実行したもの。カードは開発エージェントが Computer Use で押した。
- 実際の AI は Codex CLI の接続で、モデルは GPT-5.6-Terra を明示して選んだ。必須 Skill の正式な lane（Claude Opus 5.5 / Claude CLI、GPT-6.1 Terra / Codex CLI）は実行していない。**この記録の PASS は補助の結果。**
- 記録の取り方: アプリの前面の切り替えの log、画面の窓の順番（前から後ろ。窓の名前は読まない）、クリップボードの変更回数。
- 試験用のアプリ（自作。窓は利用者の窓の後ろに置く）: 終了を頼まれると確認のシートを出して待つもの、窓を閉じたまま持つもの、シートとポップオーバーと 2 つ目の窓を持つもの、窓を閉じても動き続けて開き直しの依頼で窓を出すもの。

## 1. 窓が別の Space にあって読めない時の案内（[PR #1345](https://github.com/Robbits-CO-LTD/sprint-coder/pull/1345)）

利用者が全画面の Chrome を使っている最中に、CLI を直接実行した。

| コマンド                            | 直す前（main の build）                                          | 直した後（`6b42b9dc`）                                                                                                  |
| ----------------------------------- | ---------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------- |
| `launch Calculator`                 | 成功。`window` も案内も無い                                      | 成功。`suggestion` に「窓は画面の外にあり、アクセシビリティに出ていない。起動を繰り返さない」と、原因と、すること       |
| `list-windows --app Calculator`     | 空の配列だけ                                                     | `data` は空の配列のまま、結果の外側に `suggestion`                                                                      |
| `snapshot --app Calculator`         | `WINDOW_NOT_FOUND`「has no matching window」「窓が出るのを待て」 | `WINDOW_NOT_FOUND`（同じ code）。文と `details`（`kind: window_off_screen_not_exposed`、`possible_causes`）が新しい案内 |
| `snapshot --window-id <計算機の窓>` | 「not exposed through accessibility」「画面に出して」            | 同じ code のまま、新しい案内                                                                                            |

- 実行の間、アプリの前面の切り替えは 0 件。
- 同じ印（画面の外・アクセシビリティに無い）は、アプリが窓を閉じたまま持っている時にも出る。見分ける公開の方法が無いので、案内は 2 つの原因を並べて言う。窓を閉じたまま持つ試験用のアプリで、4 つの経路とも同じ案内が出ることを確かめた。
- batch の中の `list-windows --app` の案内は、その step の entry にだけ付く（順番を入れ替えた 2 通りで確かめた）。
- 別の Space の窓を読む公開の API は見つからなかった。制限そのものは残る（[Issue #1336](https://github.com/Robbits-CO-LTD/sprint-coder/issues/1336) は開けたまま）。

## 2. アプリを閉じる操作（[PR #1347](https://github.com/Robbits-CO-LTD/sprint-coder/pull/1347)）

直す前の測定（main の build、CLI を直接実行）:

| 場面                                            | 結果                                                                                                                                                                                                                  |
| ----------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| ふつうのアプリ（計算機・辞書。前日からの 5 回） | 開始の 0.17〜0.24 秒後に終了。前面になったアプリの記録は無い                                                                                                                                                          |
| 終了を頼まれると確認のシートを出すアプリ        | 前面のアプリにならない。入力も使わない。シートを出した窓は、利用者が使っている窓のすぐ後ろまで上がる（前面のアプリに見えている窓が無い時は、一番前まで上がる）。コマンドは 5 秒後に `TIMEOUT`「busy or unresponsive」 |

直した後（製品の経路）:

| #   | 確かめたこと                                         | 結果 | 実際に起きたこと                                                                                                                                                                                                                               |
| --- | ---------------------------------------------------- | ---- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 1   | `close-app Calculator` のカード                      | PASS | 表示「マウスとキーボードは使いません」、注記「アプリに終了を頼みます。マウスとキーボードは使いません。保存していない変更があると、アプリが確認の窓を前に出して、閉じずに待つことがあります。」、選択肢は「今回のみ許可」「Task中許可」「拒否」 |
| 2   | 許可して閉じる                                       | PASS | exit 0、`delivered_verified`。前面の切り替え 0 件                                                                                                                                                                                              |
| 3   | 確認を出して閉じないアプリ                           | PASS | `TIMEOUT`（「accepted the request to quit but is still running」、`pending_dialog: true`）。AI は「まだ起動中です。保存確認などのダイアログが表示され、利用者の操作待ちになっている可能性があります。再試行はしていません。」と報告した        |
| 4   | `clipboard-clear` のカード（#1338 で残っていた確認） | PASS | 題「クリップボードを空にします」。拒否すると `canceled`、クリップボードの変更回数は変わらない                                                                                                                                                  |

## 3. Team のカーソル（[PR #1350](https://github.com/Robbits-CO-LTD/sprint-coder/pull/1350)）

シート・ポップオーバー・同じアプリの 2 つ目の窓（B）を持つ試験用のアプリで、AI の操作（シートの中のボタンを押す、窓のボタンを押す）の後の窓の順番を記録した（CLI を直接実行。カーソルは 1 人につき窓 4 枚）。

| 場面                                             | main の build                               | 直した後（`20dd9656`）                                  |
| ------------------------------------------------ | ------------------------------------------- | ------------------------------------------------------- |
| B が後ろ。窓の順番（前 → 後ろ）                  | カーソル → シート → ポップオーバー → 窓 → B | 同じ                                                    |
| B がシートの前                                   | B → カーソル → シート → ポップオーバー → 窓 | 同じ                                                    |
| ほかのアプリの窓の上にカーソルが出たか           | 出ない                                      | 出ない                                                  |
| アプリの窓が消えてから、カーソルの窓が消えるまで | 1.72 秒、1.76 秒                            | 0.32 秒、0.22 秒、0.40 秒（アプリを隠した時は 0.33 秒） |

- [Issue #1340](https://github.com/Robbits-CO-LTD/sprint-coder/issues/1340) の 1 つ目（シートの下にカーソルが隠れる）は、**測ると起きていなかった**。Issue の記述は、測っていない推測だった。そのための変更は入れていない。
- 窓を最小化した時の速さは測れていない（試験用のアプリが最小化できなかった）。
- ref を指定した `hover` と `drag` が、カーソルの指示に窓を名指していないことがコードで分かった。前面と pointer を使う操作で、利用者の作業中は実機で確かめられないので、[Issue #1351](https://github.com/Robbits-CO-LTD/sprint-coder/issues/1351) にした。

## 4. 窓を閉じたまま動いているアプリ（[Issue #1346](https://github.com/Robbits-CO-LTD/sprint-coder/issues/1346) の測定）

| 手順                                                                                                                | 結果                                                                                                                        |
| ------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------- |
| 窓を全部閉じて動いているテキストエディットに、main の後の build で `list-windows --app`・`snapshot --app`・`launch` | 窓は 0 件、「has no matching window」「窓が出るのを待て」、`launch` は窓も案内も無い成功                                    |
| 窓を閉じた試験用のアプリを、前面に出さない指定で開く（Dock のアイコンを押した時と同じ依頼）                         | アプリは窓を出した。前面のアプリにはならない（切り替え 0 件）。窓は、利用者が使っている窓のすぐ後ろに入った。その後は読める |

- 実際のアプリで試すと、アプリが利用者の前の状態を復元する（プレビューは、前に最小化されていた書類の窓を復元した。すぐ閉じて元に戻した）。測定は試験用のアプリで行った。
- 最小化した窓だけがあるアプリに同じ依頼を送ると、その窓が画面に戻る。依頼は、最小化した窓が無い時だけにする。

## 確かめていないもの

- 必須 Skill の正式な lane。Claude CLI での実 AI の試験（試験用の環境で Claude Code の login が要る）。
- 物理の pointer とキーボード（`--headed`）、`hover`、`drag` の実機の確認（利用者の作業中は実行していない）。
- 人数の多い Team での、カーソルの確認（0.2 秒ごと）の負荷。
- 開発者 ID で署名して公証した配布版（[Issue #1315](https://github.com/Robbits-CO-LTD/sprint-coder/issues/1315)）。Windows の実機（Windows の挙動は変えていない）。
