## 症状と影響

公開モデルカタログのresponseが8 MiB上限を超えるとUIには失敗が返りますが、response bodyはcancelされません。上流が送信を続ける場合、不要になったcatalog通信とstream資源が残ります。

## 再現手順

1. 5 MiB chunkを継続生成し、`cancel()`呼出しを記録するローカル`ReadableStream`をcatalog fetchへ返す。
2. Hugging Face catalog queryを1回実行する。
3. 8 MiB超過後のerror codeとstreamのcancel状態を確認する。

Node 22では3 chunk目で`invalid_response`になりましたが、streamの`cancel()`は呼ばれませんでした。

## 期待した結果と根拠

bounded readerが上限超過で読取りを中止するときはbodyをcancelして通信資源を解放するべきです。同リポジトリのProvider SSE bounded readerは失敗時に`reader.cancel()`を実施しています。

## 実際の結果

`readBoundedText`は例外時にも`reader.releaseLock()`だけを呼び、underlying sourceをcancelしません。大きすぎる`Content-Length`をheaderで拒否する経路ではreader取得前にthrowし、bodyへ何も行いません。

## 根本原因

`apps/desktop/src/main/public-model-catalog.ts`の`readBoundedText`が、正常EOFと上限超過を区別せず、finallyでlock解放だけを実行しています。Web Streamsのlock解放はstream cancelではありません。

### 原因経路

catalog response受信 → byte上限超過 → throw → reader.releaseLock → fetch bodyは未cancel → callerへerrorだけ返る。

### 確認した証拠

- Runtime: 合成streamは上限超過後も`cancelCalled=false`だった。
- Code: `readBoundedText`に`reader.cancel()`またはbody cancelがない。
- Comparison: `readBoundedServerSentJson`は異常終了時にreaderをcancelする。

### 除外した代替原因

- 上限判定が動いていないわけではない。query結果は`invalid_response`になった。
- 合成stream固有の問題ではない。Web Streamsでは`releaseLock()`と`cancel()`は別操作であり、cancel callbackで差を実測した。

## 影響範囲と非対象

Hugging Face APIとLocalAI Galleryのcatalog response readerが対象です。モデルartifact本体のdownload readerは別Issueです。
