## 症状と影響

OpenAI互換のChat Completionsストリームが空のまま終了、途中で切断、またはerror frameだけを返した場合でも、Turnが正常完了として扱われます。空回答や途中までの回答が成功として保存され、retryableなProvider障害を再試行できません。

## 再現手順

1. `normalizeOpenAIChatCompletionsStream`へ次の3種類のローカル`ReadableStream`を渡す。
   - byteを1件も返さずEOF
   - `output_delta`相当を1件返してEOF（終端markerなし）
   - `{ error: ... }`だけをSSE frameで返してEOF
2. canonical event typeを収集する。

Node 22での実測結果:

- 空stream: `resolution, usage, completed`
- 途中切断: `output_delta, resolution, usage, completed`
- error-only: `resolution, usage, completed`

## 期待した結果と根拠

Provider streamは明示的な正常終端を確認した場合だけ`completed`を発行し、空・途中切断・error-onlyは`error`または「completion eventなし」として失敗するべきです。MainのProvider Turn処理も`roundCompleted`がfalseなら失敗させる契約を持っています。Closed Issue #135の受入条件にも、EOFでcompleted eventがない場合はfailedを維持すると明記されています。

## 実際の結果

入力内容に関係なく、iteratorのEOF到達後に`resolution`、`usage`、`completed`が無条件で生成されます。

## 根本原因

`apps/desktop/src/main/openai-chat-completions-stream.ts`の`normalizeOpenAIChatCompletionsStream`が、Provider由来の正常終端を追跡せず、reader loop終了後に`completed`を合成しています。また、Chat Completionsのerror frameを判定する分岐がありません。

### 原因経路

Providerの空・切断・error-only SSE → bounded readerがEOF → normalizerが無条件に`completed`をyield → `ipc.ts`の`roundCompleted`がtrue → Turn成功。

### 確認した証拠

- Runtime: Node 22の合成streamで3条件すべてが`completed`になった。
- Code: normalizerは終端flagを持たず、loop後に常に`completed`をyieldする。
- History: #135を閉じたPR #141はdeadlineとMain側のcompletion検査だけを変更し、このnormalizerは変更していない。

### 除外した代替原因

- Main側のcompletion検査欠落ではない。`ipc.ts`は`roundCompleted`がfalseなら明示的に失敗させる。
- SSE readerの容量制限欠落ではない。bounded readerはquota超過時に例外とcancelを実施する。

## 影響範囲と非対象

Chat Completions protocolを使うOpenAI互換ProviderとManaged Local通常応答が対象です。Responses、Anthropic、Geminiのnormalizer変更は非対象です。
